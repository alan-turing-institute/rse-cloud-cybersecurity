# 01 — The Scenario

A minimum-cost Azure environment, built with the [tech stack](tech-stack.md), consisting of:

1. A **storage account**.
2. An **Azure Database for PostgreSQL** instance.
3. A **virtual machine** that can read/write blobs in the storage account and run SQL queries against the PostgreSQL database.
4. **Unit tests** for the Pulumi program using Pulumi's mocking framework.

## Design principles

- **Minimum cost first.** Every SKU/tier choice below picks the cheapest option that still satisfies the scenario, unless a more secure alternative costs materially the same — in which case the secure option wins (see next point).
- **Secure by default, at no extra cost.** This repo supports a cloud-security presentation, so the plan avoids public exposure and long-lived secrets wherever doing so doesn't increase the bill:
  - PostgreSQL is reachable only from inside the virtual network (VNet-integrated "private access"), not from the public internet.
  - The VM authenticates to the storage account via a system-assigned **managed identity** and an RBAC role assignment — no storage account keys or connection strings are generated or stored.
  - SSH to the VM is restricted by an NSG rule to a single trusted IP address, supplied via Pulumi config (no `0.0.0.0/0`).
  - The database admin password (needed for `psql` from the VM) is generated by Pulumi as a random secret and exposed only as a stack secret output — never hardcoded.
- Single resource group, single region (config `azure-native:location`, currently `westeurope`), single environment (`dev` stack) — no multi-region or HA requirements for this scenario.

## Estimated cost

Rough order of magnitude, West Europe, pay-as-you-go — enough to sanity-check "minimum cost," not a quote:

| Resource | SKU | ~Monthly cost |
|---|---|---|
| VM | `Standard_B1s` (1 vCPU, 1 GiB, Burstable) | ~$8 |
| VM OS disk | Standard HDD (`Standard_LRS`) managed disk | ~$2 |
| PostgreSQL Flexible Server | `Standard_B1ms` (Burstable), 32 GB storage | ~$25–30 |
| Storage account | `Standard_LRS`, `StorageV2`, negligible usage | ~$1–2 |
| Public IP | Standard SKU, static (Basic SKU is retired) | ~$3–4 |
| Private DNS zone + VNet link | — | ~$0 (well within free tier) |
| **Total** | | **~$40–50/month** |

The dominant cost is the PostgreSQL compute tier — there isn't a materially cheaper managed Postgres option on Azure below Burstable `B1ms`. If cost needs to drop further, the two levers are: turning the stack off with `pulumi destroy` between demos, or dropping PostgreSQL storage to the 32 GB minimum (already assumed above).

## Resource inventory

All resources go in the existing `rse-cloud-cybersecurity-rg` resource group (`infra.py`). Class names/import paths below are from `pulumi_azure_native` (verified against the installed SDK), Python.

### Networking

| Resource | Class | Notes |
|---|---|---|
| Virtual network | `network.VirtualNetwork` | One VNet, address space e.g. `10.0.0.0/16`. |
| VM subnet | `network.Subnet` | e.g. `10.0.1.0/24`, associated with the VM's NSG. |
| Database subnet | `network.Subnet` | e.g. `10.0.2.0/24`, **delegated** to `Microsoft.DBforPostgreSQL/flexibleServers` via `delegations=[network.DelegationArgs(name=..., service_name="Microsoft.DBforPostgreSQL/flexibleServers")]`. Required for VNet-integrated Postgres. |
| NSG | `network.NetworkSecurityGroup` | One inbound allow rule: TCP/22 (SSH) from a single trusted IP (Pulumi config, e.g. `ssh-allowed-ip`), priority 100. Default deny for everything else (implicit). |
| Public IP | `network.PublicIPAddress` | `sku=PublicIPAddressSkuArgs(name=PublicIPAddressSkuName.STANDARD)`, `public_ip_allocation_method=IPAllocationMethod.STATIC` (Standard SKU requires static; Basic SKU is retired). |
| NIC | `network.NetworkInterface` | Attaches the VM subnet + public IP; NSG is set on the subnet. |
| Private DNS zone | `privatedns.PrivateZone` | Zone name `privatelink.postgres.database.azure.com`, required for VNet-integrated Postgres name resolution. |
| VNet link | `privatedns.VirtualNetworkLink` | Links the private DNS zone to the VNet. |

### Storage account

`storage.StorageAccount`:
- `kind=storage.Kind.STORAGE_V2`
- `sku=storage.SkuArgs(name=storage.SkuName.STANDARD_LRS)`
- `location`, `resource_group_name` from the existing resource group.
- Consider `access_tier=storage.AccessTier.HOT` (default) — fine for light demo usage; no lifecycle policy needed at this scale.
- A single blob container (`storage.BlobContainer`) for the VM to read/write against.

### PostgreSQL (Flexible Server)

`dbforpostgresql.Server`:
- `sku=dbforpostgresql.SkuArgs(name="Standard_B1ms", tier=dbforpostgresql.SkuTier.BURSTABLE)`
- `storage=dbforpostgresql.StorageArgs(storage_size_gb=32)` (minimum)
- `version="17"`
- `backup=dbforpostgresql.BackupArgs(backup_retention_days=7, geo_redundant_backup="Disabled")` (7 days is already the minimum/default)
- `network=dbforpostgresql.NetworkArgs(delegated_subnet_resource_id=<db subnet id>, private_dns_zone_arm_resource_id=<private zone id>)` — this is what makes the server VNet-integrated/private instead of publicly reachable; mutually exclusive with public network access + firewall rules.
- `administrator_login` + a Pulumi-generated `administrator_login_password` (see [Secrets](#secrets-and-config) below).
- One `dbforpostgresql.Database` for the working database used by the demo queries.

### Virtual machine

`compute.VirtualMachine`:
- `hardware_profile=compute.HardwareProfileArgs(vm_size="Standard_B1s")`
- Ubuntu LTS image reference (no Windows licensing cost).
- OS disk: `compute.OSDiskArgs(managed_disk=compute.ManagedDiskParametersArgs(storage_account_type="Standard_LRS"), create_option="FromImage")`.
- `network_profile` referencing the NIC above.
- `identity=compute.VirtualMachineIdentityArgs(type=compute.ResourceIdentityType.SYSTEM_ASSIGNED)` — used for storage access, no keys involved.
- `os_profile.custom_data` — base64-encoded cloud-init that installs `postgresql-client` (for `psql`) and the Azure CLI/`azcopy` or SDK tooling needed to touch blobs using the managed identity. Simpler than a separate `VirtualMachineExtension` for a one-shot package install.

### RBAC

`authorization.RoleAssignment`:
- `principal_id=vm.identity.principal_id`
- `role_definition_id` = built-in **Storage Blob Data Contributor** role (`ba92f5b4-2d11-453d-a403-e96b0029c9fe`), scoped to `storage_account.id`.
- `principal_type="ServicePrincipal"`.

This is what lets the VM read/write blobs without any storage key ever being generated or handed to it.

## Secrets and config

- `administrator_login_password` for Postgres: generate with `pulumi.random.RandomPassword` (or equivalent), mark as a Pulumi secret, pass into `dbforpostgresql.Server`. Export it as a **secret** stack output so a human doing the demo can retrieve it via `pulumi stack output --show-secrets`, rather than baking it into config or a script.
- New Pulumi config values needed in `Pulumi.dev.yaml` (in addition to the existing `azure-native:location`):
  - `ssh-allowed-ip` — the single source IP/CIDR allowed to SSH into the VM.
  - `db-admin-username` — Postgres admin login name (non-secret).
  - `vm-admin-username` / VM SSH public key — for VM login (public key preferred over password auth on the VM itself).

## Module layout

Following the existing pattern (`infra.py` imported by `__main__.py` and by tests):
- Keep `infra.py` as the single module exposing all resources as module-level names (as it does today for `resource_group`), so `tests/test_infra.py` can import and assert on them the same way it already does for `resource_group`.
- If `infra.py` grows unwieldy, it can be split into per-concern modules (`networking.py`, `storage.py`, `database.py`, `compute.py`) re-exported from `infra.py` — deferred until the flat file actually becomes hard to navigate, not upfront.

## Testing plan

Extend `tests/test_infra.py` using the same `pulumi.runtime.Mocks` + `pulumi.runtime.test` pattern already in place:
- One test per resource asserting its URN/type token and key inputs land as expected (e.g. storage account SKU is `Standard_LRS`, Postgres SKU tier is `Burstable`, NSG has no unrestricted inbound rule, VM has a system-assigned identity).
- A test asserting the Postgres server's `network` args reference the delegated subnet (i.e. it is not left publicly accessible).
- A test asserting the `RoleAssignment` scope points at the storage account and the role definition ID matches Storage Blob Data Contributor.
- Keep using `MockResourceArgs`/`MockCallArgs` mocks — no real Azure credentials or calls needed to run `uv run pytest`.

## Open questions / assumptions to confirm before implementing

1. **SSH exposure**: a public IP + NSG-restricted SSH is the cheapest way to reach the VM (Azure Bastion costs roughly 3–4x the rest of this stack combined). Confirm this trade-off is acceptable for the demo, versus e.g. an existing VPN/jump host.
2. **Postgres auth mode**: plan assumes password auth (simplest for a live demo running `psql`). Entra-only auth (`auth_config` with `active_directory_auth=Enabled`, `password_auth=Disabled`) would remove the password entirely and let the VM's managed identity authenticate directly — worth considering if the presentation wants to showcase passwordless DB auth too, at no cost difference.
3. **Region**: keeping `westeurope` (already configured) unless the presentation needs a different one.
4. **Basic Public IP SKU retirement**: plan assumes Standard SKU + static allocation is required (Basic retired). Worth a final live check against Azure's current SKU support at implementation time.
